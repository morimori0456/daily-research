# 新興開発ツール 日次トレンド調査

【目的】
私は自動運転 / ML / 開発ツールに関心のあるエンジニア（主要環境: Windows / WSL2 / Ubuntu x86_64 / NVIDIA Jetson AGX Thor ARM64、およびマルチエージェント運用環境）です。
「今まさに注目され始めている新しい開発者向けツール」および「既存注目ツールのメジャー機能更新」を毎日キャッチアップするための**日次トレンド調査レポート**を作成してください。
特定のツール名を固定指定はしません。直近24〜48時間（インデックス遅延等を考慮し、直近7日以内の未掲載重要項目は「【遅延発見】」として許容）の公開・更新・話題化から、実用価値の高い新興ツールを発見してください。

対象イメージ（この粒度・ジャンルのツールを想定）:
- ターミナル / CLI / AIコーディングエージェント支援 / Git・worktree 管理 / サンドボックス / ローカルLLM・RAG 周辺 / エディタ・ランタイム・ビルド/パッケージ管理・DevOps 生産性ツール。

【定番ツールの扱い】
- 既に導入・周知済みの定番ツール（`Claude Code`, `Codex`, `Antigravity`, `Ghostty`, `Herdr`, `tmux` 等）は、単なるツール紹介としては**除外**し、**メジャー新機能リリースや破壊的・重要なアップデートがあった場合のみ「【続報・更新枠】」として扱う**こと。

【探索範囲（どこを見るか）】
- 発見経路: GitHub Trending, GitHub Releases, Hacker News / "Show HN", Product Hunt, Reddit（`r/programming`, `r/commandline`, `r/LocalLLaMA` 等）, awesome 系リスト
- 技術ブログ・一次発信: Zenn, Qiita, Note, Substack, 公式ブログ・開発者ポスト
- **深掘り検索の徹底**: 1回の検索で終わらせず、採択候補ごとに `search_web` で「`ツール名 + README / install / arm64 / uninstall / benchmark`」等の追加クエリを実行し、公式ドキュメント・README の仕様を掘削してください。

【選別基準（何を採択するか）】
- 直近24〜48時間（または直近7日以内の「【遅延発見】」）で新規公開、メジャーリリース、またはコミュニティで具体的な評価・議論が確認できたもの。
- 実在し、実際にインストールして試せること（単なる構想・vaporware は原則除外）。
- 既存ツールを置き換え・補完する明確な理由があること（速度、UX、並列エージェント運用、ローカル完結性等）。
- **人気指標の厳格化**: 「star 急増」「急に言及増加」「バズ」といった表現は、比較基準や時系列データ（例: Trending の stars today 等）を `[L2: 公式リリース・アブストラクト・仕様確認済]` 相当の一次画面で確認できた場合のみ記載し、確認できない場合は「人気推移は未確認」と明記してください。作者の告知のみで「人気急上昇」と断定しないでください。

【採用件数の方針】
- **最大3〜5件**に厳選し、根拠のない順位付け（「TOP10」等）は行わないでください。
- 該当が少ない日は無理に件数を埋めず、**0〜3件（該当なし・0件も正常結果として許容）**で構いません。

【各ツールについて収集する情報】
1. **概要・カテゴリ・置き換え対象**（何をするツールか、既存の何の課題を解決するか）
2. **解消する既存環境のボトルネック（必須）**
   - 自分の既存環境（**AV/ML 開発、WSL2/Ubuntu/Jetson、マルチエージェント運用**）における**どの具体的ボトルネック・詰まりを解消するか**を必ず特定してください。既存環境への明確な効用がない場合はその旨を率直に評価してください。
3. **注目理由・根拠**（リリース内容、確認できた技術的評価・賛否。未確認のSNS反響は「未確認」と明記）
4. **最小の試し方（4点セット・コマンド創作厳禁）**
   - 必ず「**①インストール ＋ ②代表タスク1手 ＋ ③成功判定基準 ＋ ④アンインストール/クリーンアップ方法**」の4点を整理してください。
   - **検索で確認できていないコマンドの創作は厳禁**とします。公式 README / ドキュメント（`[L2: 公式リリース・アブストラクト・仕様確認済]`）で確認できたコマンドのみ（対象OS/アーキテクチャと「未検証」である旨を併記して）記載し、`[L1: 検索断片のみ・詳細未確認]` に留まる場合は未確認コマンドを掲載せず「公式コマンド未確認（L1）」と記載してください。
5. **成熟度・プラットフォーム制約・リスク**（対応OS、ライセンス、本番投入時の注意点）
   - **重要**: `Ubuntu (x86_64)` 対応の情報のみから `Jetson (ARM64)` 対応を推測・断定しないでください（ARM64 ビルドや wheel の有無が確認できた場合のみ記載し、不明なら「ARM64/Jetson 対応は未確認」と明記）。

【出力フォーマット（必須構造）】
比較表は Dashboard の `.mb-page` で視認しやすい **3〜4列** に整理してください。

【制約・品質基準】
- 確認レベルを `[L2: 公式リリース・アブストラクト・仕様確認済]` と `[L1: 検索断片のみ・詳細未確認]` で厳格に区別し、`L1` に留まるツールについては **「今すぐ試す」への分類および未確認コマンドの掲載を厳禁** とします（「様子見」とし、未確認事項に依存する導入推奨を保留してください）。
- 不確実な点・取得できなかった指標は「未確認」と明記してください。
- 日本語出力とし、技術用語（`CLI`, `GPU rendering`, `socket API`, `runtime`, `RAG`, `worktree`, `ARM64` 等）は英語のまま使用してください。
- 数式や矢印に LaTeX 記法（`$\rightarrow$` 等）を使わず、プレーンな Unicode 文字（`→`, `×`, `≥` 等）を使用してください。
